# Object-cache invariants

Moved verbatim from the former root AGENTS.md. Each rule records a defect that was fixed; do not weaken one without a test proving the replacement.

- Object caches are single-view content caches, not authorization caches. Public filtered ID reads must check visible IDs before cache lookup, including negative hits; `forUpdate` must execute a locking database read. Internal association loaders retain their existing filtered-ID loading path. Exception: a non-locking `QUERY` read of a type outside the content-only policy whose only effective filter is the built-in default logical-delete filter (no user, reversed, ignored or sharding filter) judges visibility on the cached row's logical-deleted column with `LogicalDeletedInfo.isDeleted` and issues no visible-ID query; a cached payload without that column falls back to the visible-ID query for the whole call.
- Ordinary cached to-many ID snapshots can outlive deleted or filtered targets. Association assembly omits absent objects, retaining valid order and duplicates and an empty list when all targets are absent; never insert null children. Explicit query-cache hydration still uses whole-query fallback for missing values.
- Query object-cache hydration is an explicit content-cache hint, not a query-result or statement-snapshot cache. SQL remains authoritative for membership, join topology, order, duplicates, pagination and scalar slots; fresh entity seeds use the existing readers and validate concrete cache types before shaping or DTO conversion. Missing, negative or incompatible cached values fall back to the whole original query, not a shortened page. The filtered id-only skeleton already establishes visibility, so the hint skips the redundant per-id visibility query only through an opaque, package-minted, immutable seed bound to the exact executing client, connection, manager, requested/cache-owner types and id-to-concrete-type group; the seed is re-validated (identity, `QUERY` purpose, non-locking, manager inactivity proof) before any cache access, and the caller-supplied group is snapshotted into an immutable copy *before* that authentication and only that copy is used for visibility and concrete-type validation, so an arbitrary `ids` iterable cannot widen the admitted group. Hydration rebinds the entities reader to the query's executing client (`forSqlClient`), because a delegating client returns the underlying reader and the seed identity must still match. The public raw `EntitiesImpl.findMapByIdsForQuery` and every ordinary filtered read keep their visibility check.
- Object-cache query hints require positive proof of an inactive transaction on the connection owned by the executing manager scope. External, mismatched or unknown connections and locking or command reads must not publish query content into shared caches.
- Explicit Fetcher content masks approve stored leaves, not association edges or authorization facts. Keep unapproved values, protected metadata, presence and exact target admission SQL-authoritative; preserve native formula dependencies and original visibility. Validate the whole page before any DTO converter runs.
- Declined content masks execute the complete cache-disabled graph in an isolated fetcher context, including transactional, locking, command, reselected and streaming paths. Recursive projections and masked field-local filters conservatively decline. Ordinary ID reads and boolean/no-argument hints retain their legacy semantics for types without the content-only policy. Opted-in caches admit content derived from the executed native projection, so a newly projected stored leaf participates automatically; no-argument hints reuse that derivation with existing DTO Language projections, without handwritten consumer fetchers.
- Apply content masks to native `forType` branches using SQL's concrete type. Admit cache seeds per fresh concrete carrier only when its applicable approved leaves (including embedded leaves) are missing from SQL; a carrier with no such missing content stays fresh and does not require an object cache. Continue descending into navigated nodes independently. Keep universally selected leaves and ambiguous parent-branch paths SQL-fresh unless approval is proven for every applicable carrier. Decline optional reduction when required native metadata is unavailable; never cast public interfaces blindly or restrict ordinary reads.
- Quarkus entity caches may opt into `content-only`: the object cache remains available to automatic content admission, while ordinary entity/DTO lookups and association loaders bypass cached entity snapshots and edge mappings. Admitted leaves are derived from each executed projection (stored scalars only, including single-table branches); associations, formulas, ID views and protected metadata stay SQL-fresh. No per-field cache list is configurable. A base entity's policy covers its derived types and subtype-declared fields. The default remains legacy cache behavior; this policy does not make a general transaction-safety promise for other cache users.
- Admission is derived from each selected native projection, not from a configured DTO shape. Scalar-only, ID-only and unsupported projections stay fresh without cache access. Explicit Fetcher masks retain strict selected-content validation.
- Propagate filter parameters through every tier of a parameterized cache chain. Declarative Quarkus factories use native `FilterState` and multi-view binders for filtered associations in LOCAL_ONLY, REMOTE_ONLY and FULL modes. Invalidation deletes every view for an owner key.
- The Quarkus connection manager hands out a deferred connection (`LazyConnection`): the pool is asked only at the first real JDBC call, so a fully cache-served read takes no pooled connection and enlists nothing. The proxy is the TSR resource and the connection identity for seeds and transaction proofs; the auto-commit probe acquires it.
- `BINLOG_ONLY` mutations report keys through `MutationKeyListener` (core: `ast/impl/mutation/MutationKeys`, gated by trigger type, a listening connection manager and a cache keyed by the mutated type or property). The Quarkus manager evicts object and owning-side property caches after `STATUS_COMMITTED` (auto-commit: after the scope's connection closes); rollback evicts nothing; user connections are ignored; cache errors are logged, never thrown. Only when that gate holds, a bulk update returns ids through `UPDATE ... RETURNING` (one id pre-select on dialects without it) and a bulk delete selects ids once, then runs the same direct `DELETE` it would without a listener: the listener must never change which statement runs or which constraint error surfaces.
